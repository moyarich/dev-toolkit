# Package documentation

Package documentation in `dev-toolkit` uses a predictable, filesystem-based routing convention so documentation can be discovered, ordered, and rendered without package-specific configuration.

Do not place unrelated loose Markdown files directly under a package's `docs/` directory. Use an ordered navigation structure with a root `page.mdx` and a `page.mdx` for each navigable documentation page.

## Documentation contract

A package documentation tree follows these rules:

1. `docs/page.mdx` is the package documentation landing page.
2. Every navigable page lives in its own directory and is named `page.mdx`.
3. Numeric prefixes such as `01-`, `02-`, and `03-` define stable navigation order.
4. Directory names after the numeric prefix are descriptive, lowercase, and hyphenated.
5. Nested sections use the same convention recursively.
6. Relative links point to the target `page.mdx`.
7. The package `README.md` remains the concise package entry point; detailed material lives in `docs/`.

This convention keeps the documentation tree both human-readable in GitHub and directly consumable by filesystem-driven documentation tooling.

## Recommended folder tree

```text
packages/
└── my-package/
    ├── README.md
    ├── CHANGELOG.md
    ├── package.json
    └── docs/
        ├── page.mdx
        ├── 01-getting-started/
        │   └── page.mdx
        ├── 02-guides/
        │   ├── 01-first-workflow/
        │   │   └── page.mdx
        │   └── 02-advanced-workflow/
        │       └── page.mdx
        └── 03-reference/
            ├── 01-cli/
            │   └── page.mdx
            └── 02-api/
                └── page.mdx
```

The numeric prefixes define a stable, human-readable navigation order. They are part of the documentation source layout, not the visible page title.

## Route mapping

Treat each `page.mdx` as the content for its containing directory.

For example:

```text
docs/page.mdx
docs/01-getting-started/page.mdx
docs/02-guides/01-release/page.mdx
docs/03-reference/01-cli/page.mdx
```

forms this logical hierarchy:

```text
/
├── getting-started
├── guides/
│   └── release
└── reference/
    └── cli
```

The source directory controls ordering while the page heading controls the human-facing title.

## Root documentation page

Every package documentation tree should begin with:

```text
docs/page.mdx
```

Use it as a concise landing page and navigation index:

```mdx
# My Package

`@moyarich/my-package` provides ...

## Start here

- [Getting started](./01-getting-started/page.mdx)
- [First workflow](./02-guides/01-first-workflow/page.mdx)
- [CLI reference](./03-reference/01-cli/page.mdx)
```

## Recommended sections

Use these sections when they fit the package:

```text
01-getting-started/
02-guides/
03-reference/
```

Packages can add domain-specific sections when useful. For example, a component library can use `02-components/`, and a package centered on runtime internals can use `02-architecture/`.

Prefer semantic folder names over forcing every package into an identical taxonomy.

## One page per directory

Each navigable document should use:

```text
<ordered-name>/page.mdx
```

Prefer:

```text
docs/02-guides/01-release/page.mdx
```

instead of:

```text
docs/release.md
docs/guides-release.md
```

This keeps routing, navigation, and documentation discovery predictable.

## README versus docs

The package `README.md` should stay concise:

- package purpose
- minimal installation or usage
- a short example when useful
- links into `docs/`

Detailed guides, tutorials, architecture notes, testing notes, and reference material belong under `docs/`.

## package.json

Publishable packages should normally include documentation in `package.json#files`:

```json
{
  "files": ["bin", "src", "docs", "README.md", "CHANGELOG.md"]
}
```

Adjust the runtime directories for the package, but keep `docs` when the package documentation should ship with the published artifact.

Private or source-only packages can omit `docs` from the published-file list when no package artifact is produced.

## Adding a new guide

For a second guide under `02-guides`:

```sh
mkdir -p packages/my-package/docs/02-guides/02-new-guide
```

Create:

```text
packages/my-package/docs/02-guides/02-new-guide/page.mdx
```

Then add it to `docs/page.mdx` or the appropriate parent/index page.

## Documentation checklist

Before merging package documentation:

- `docs/page.mdx` exists
- navigable pages use `page.mdx`
- ordered folders use two-digit numeric prefixes
- page and folder names are descriptive and hyphenated
- nested sections repeat the same routing pattern
- links are relative and point to `page.mdx`
- detailed content is kept out of the package README
- `package.json#files` includes `docs` when docs should be published
- obsolete loose `.md` files are removed after migration
- examples use current package names and commands

Use an existing package with a complete `docs/page.mdx` tree as the reference shape when creating or restructuring package documentation.
