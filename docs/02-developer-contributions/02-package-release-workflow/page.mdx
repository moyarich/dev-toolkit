# Package release workflow

The repository release system treats drafting, releasing, and publishing as separate stages of one package release lifecycle.

The goal is to keep the package version, Git tag, GitHub Release, and package registry state aligned while still allowing a release to stop safely before publication.

## Release lifecycle

A normal package release progresses through these states:

```text
package changes on main
        ↓
Draft package release
        ↓
GitHub Release: draft
        ↓
Release
  - resolve version
  - validate canonical release identity
  - create release commit when required
  - create canonical Git tag
  - push commit and tag
        ↓
GitHub Release: still draft
        ↓
Package publish
        ↓
GitHub Release: published
```

A release-only run intentionally stops after the Git tag is pushed. The GitHub Release remains a draft until package publication succeeds.

A later standalone publish can continue that same release and publish the existing draft.

## Canonical release identity

Draft, release, and publish workflows use the same release identity generated by `@moyarich/workspace-tools`.

The rules are:

```text
Git tag:             <package-directory>@<version>
GitHub Release name: <package-name> v<version>
```

For example:

```text
Package name:        @moyarich/auto-glow-md
Package directory:   packages/moyarich-auto-glow-md
Version:             0.1.0

Git tag:             packages/moyarich-auto-glow-md@0.1.0
GitHub Release name: @moyarich/auto-glow-md v0.1.0
```

Use the shared CLI when another workflow or tool needs these values:

```sh
workspace-release-identity packages/moyarich-auto-glow-md \
  --version 0.1.0 \
  --json
```

Do not reproduce the tag or release-name formula independently in workflow YAML or shell scripts.

## 1. Draft package release

`.github/workflows/release-drafter.yml` maintains package-specific GitHub Release drafts.

For a first release, the workflow prefers the matching package `CHANGELOG.md` section. If no matching section exists, it falls back to package-specific Git history and groups conventional commits into release-note categories.

For later releases, the generated Release Drafter configuration uses the same canonical release identity.

The draft includes:

- the canonical release name
- the canonical package Git tag
- package-specific release notes
- an exact installation command

The draft does not itself publish a package or complete the GitHub Release.

## 2. Release package

`.github/workflows/reusable_npm-release.yml` performs the release operation.

Before a real release, it verifies that the exact matching GitHub Release draft already exists and that its name matches the canonical release identity.

Depending on the selected version mode, the release command may update the package version and changelog before creating the release commit.

The release then creates the canonical Git tag and pushes the release commit and tag.

At this point:

```text
Git tag:        exists
GitHub Release: draft
Package:        not necessarily published
```

That is an intentional and valid state.

### Release-only run

When `publish=false`:

```text
release commit/tag    created
GitHub Release        draft
package publication   not requested
```

The GitHub Release is not promoted merely because the Git tag exists.

### Release and publish run

When `publish=true`, the same workflow continues into package publication. The GitHub Release is promoted only after package publication succeeds.

## 3. Publish package

Package publication uses `workspace-publish` through either the combined release workflow or `.github/workflows/reusable_npm-publish.yml`.

Publishing verifies the canonical package tag by default:

```text
<package-directory>@<package.json version>
```

The tag must exist and point to the expected commit unless tag verification is explicitly disabled.

A real standalone publish also verifies that the matching GitHub draft exists and has the expected canonical release name.

After registry publication succeeds, the workflow publishes that existing GitHub Release draft instead of creating a second release.

## Draft finalization

The GitHub Release is promoted with the same:

- release ID
- tag
- release name
- release notes

Only its draft state changes.

```text
draft=true
    ↓ package publication succeeds
draft=false
```

This keeps the draft created during development as the authoritative GitHub Release record.

## npm staged publication

npm publication can enter a staged state before the registry release is fully complete.

When the publish result is staged, the GitHub Release remains a draft.

```text
npm publication:      staged
GitHub Release:       draft
```

The release should not be presented as complete until registry publication has actually completed.

## Valid release states

The draft workflow distinguishes valid release progress from inconsistent release history.

| Git tag | Draft release | Published release | Meaning |
| --- | --- | --- | --- |
| no | no | no | No release prepared yet |
| no | yes | no | Normal pre-release draft |
| yes | yes | no | Valid release in progress |
| yes | no | yes | Completed release |
| yes | no | no | Orphan tag; workflow blocks |
| yes | yes | yes | Inconsistent state; investigate |

A Git tag with a matching draft is deliberately accepted because release-only runs leave the release in that state.

A Git tag with neither a matching draft nor a published GitHub Release is treated as an orphan and requires reconciliation.

## Why the release stays draft after tagging

Creating a Git tag proves that a version was identified in Git. It does not prove that package publication completed successfully.

Keeping the GitHub Release as a draft prevents this misleading state:

```text
GitHub Release: published
Package registry: failed or incomplete
```

The public GitHub Release therefore represents completed package publication rather than merely completed Git tagging.

## Workflow responsibilities

| Component | Responsibility |
| --- | --- |
| `release-drafter.yml` | Maintain package-specific release notes and GitHub drafts |
| `workspace-release-identity` | Generate the canonical tag and release name |
| `workspace-release` | Resolve version, update release files, create commit and Git tag |
| `workspace-publish` | Validate and publish package artifacts |
| `reusable_npm-release.yml` | Orchestrate release and optional immediate publish |
| `reusable_npm-publish.yml` | Publish an already released/tagged package and finalize its draft |

## Safety rules

Release tooling should preserve these invariants:

1. Draft, release, and publish use the same canonical release identity.
2. A real release requires the matching GitHub draft.
3. Release tags are immutable and are never force-moved.
4. Package publishing verifies the canonical release tag by default.
5. Release-only runs leave the GitHub Release as a draft.
6. The GitHub Release is published only after package publication succeeds.
7. Staged npm publication does not publish the GitHub Release.
8. A tag without a matching draft or published release is treated as an orphan.
9. Existing tagged drafts are preserved instead of regenerated.
10. Dry runs do not mutate repository, registry, tag, or GitHub Release state.

## Typical first release

For a package already at `0.1.0`:

```text
1. Merge package changes to main
2. Draft package releases workflow creates:
   @moyarich/example v0.1.0
3. Review/edit the draft release notes
4. Run the release workflow
5. Release workflow creates:
   packages/example@0.1.0
6. GitHub Release remains a draft
7. Publish the package
8. Publish workflow promotes the existing draft
9. GitHub Release is now public
```

If release and publish are requested in the same run, steps 4 through 8 are orchestrated by the release workflow.
